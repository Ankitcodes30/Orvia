# Release Process

Orvia releases are built by a manual GitHub Actions workflow and published as
prereleases. There is no automated release on push.

## Versioning

- The app version lives in `pubspec.yaml` (`version: 3.0.4+0`).
- The workflow keeps the version name and replaces the build number with the
  GitHub Actions run number.
- Release tags use `v<version>+<run_number>`, for example `v3.0.4+123`.
- Plugin versions are separate integer strings; see
  [Manifest and packaging](../plugins/manifest-and-packaging.md).

## Workflow

File: `.github/workflows/main.yml`

Trigger: `workflow_dispatch` (manual).

| Job | Runner | Output |
|---|---|---|
| `build-windows-android` | `windows-latest` | Android APKs and Windows zip |
| `build-linux` | `ubuntu-latest` | Linux tar.gz |

Both jobs publish to the same release tag. The Windows/Android job creates the
release; the Linux job updates it with `allowUpdates: true`.

### Android

The workflow builds:

- `orvia_android_v<version>+<run>_universal.apk`
- `orvia_android_v<version>+<run>_armeabi-v7a.apk`
- `orvia_android_v<version>+<run>_arm64-v8a.apk`
- `orvia_android_v<version>+<run>_x86_64.apk`

It writes `android/key.properties` and `android/orvia.jks` from secrets, builds
with `--split-per-abi`, and verifies each APK with `apksigner`. Local release
builds without `android/key.properties` fall back to debug signing, so do not
publish those artifacts.

Required secrets:

| Secret | Purpose |
|---|---|
| `KEY_STORE` | Base64-encoded JKS keystore. |
| `KEY_PASSWORD` | Key password. |
| `STORE_PASSWORD` | Keystore password. |
| `KEY_ALIAS` | Key alias. |
| `SECRET_KEY` | GitHub token used by the release action. |

### Windows

The workflow builds `flutter build windows --release`, renames the executable to
`Orvia.exe`, and zips the release bundle. The zip is not code-signed by the
workflow.

### Linux

The workflow installs GTK/clang/ninja dependencies, builds
`flutter build linux --release`, and packages the bundle as a `.tar.gz`. It is
not code-signed by the workflow.

### Release metadata

- Every release is created with `prerelease: true`.
- `allowUpdates: true` lets the Linux job add assets to the release created by
  the Windows/Android job.
- The release body is not generated by the workflow; write release notes
  manually.

## CI checks

File: `.github/workflows/checkout.yml`

Triggers:

- Push to `main`, ignoring Markdown, `LICENSE`, `fastlane/**`,
  `.github/FUNDING.yml`, and `ghpage/**`.
- Pull requests targeting `main`.

Jobs:

| Job | Command |
|---|---|
| Flutter Analyze & Test | `flutter pub get`, `flutter analyze --no-fatal-infos` |
| Rust Clippy & Test | `cargo check --manifest-path rust/Cargo.toml` |

Despite the job names, the workflow currently runs **no tests and no clippy**.
Do not rely on CI to catch test failures. Run `flutter test` and the Rust tests
locally when changing behavior.

## Local release checklist

1. Update `version` in `pubspec.yaml`.
2. Update `CHANGELOG.md` with user-visible changes.
3. Run `flutter pub get`.
4. Run `flutter analyze --no-fatal-infos`.
5. Run `flutter test`.
6. Run `cargo check --manifest-path rust/Cargo.toml`.
7. Run `cargo test --manifest-path rust/Cargo.toml` if Rust behavior changed.
8. Build and smoke-test the target platform.
9. Confirm Android signing when producing APKs.
10. Trigger **Build & Release** manually and select the `main` branch.
11. Verify the release tag, assets, and release notes. The workflow does not
    publish checksums.
12. Announce the release and update the website if needed.

## Fastlane metadata

`fastlane/metadata/android/en-US/` contains store listing text and images. There
is no `Fastfile` in this repository, so fastlane is not used to build or publish
releases automatically. Treat it as metadata for store uploads.

## Website deployment

The Svelte site lives in `ghpage/`.

```bash
cd ghpage
npm install
npm run build
python ../deploy_page.py
```

`deploy_page.py` builds the site if `ghpage/build` is missing, copies
`CHANGELOG*` and `ghpage/repositories.json` into the build when present, pushes
the result to the `ghpage` branch, and force-updates that branch. It reuses an
existing `ghpage/build`, so delete that directory to force a fresh build after
site changes.

Important: `deploy_page.py` expects `ghpage/repositories.json`, but that file is
not currently present. As a result, the hosted catalogue at
`https://hemantkarya.github.io/Orvia/repositories.json` returns 404. Create the
catalogue before relying on hosted plugin discovery, or use the fallback
catalogue URL in the app.

The canonical Pages site is <https://ankitcodes30.github.io/Orvia/>, but the
app's bootstrap constants still point at the legacy `hemantkarya.github.io`
catalogue URLs. Update `lib/services/plugin_bootstrap_service.dart` when moving
the catalogue to the canonical site.

Alternative deploy path:

```bash
git add ghpage/build
git commit -m "build"
git subtree push --prefix ghpage/build origin ghpage
```

## Rollback

- Delete or edit the GitHub release and re-point users to the previous tag.
- Do not reuse a version tag with different contents.
- If a plugin update is bad, publish a new higher integer plugin version; the
  app does not support downgrades through the normal update path.
